# Decision Log

### 決定：EC2をPrivate Subnetに配置する

- **状況**：EC2をPublic Subnetに配置すれば構成を簡単にできるが、インターネットからEC2へ直接アクセスできる状態になる。
- **選んだもの**：EC2はPrivate Subnetに配置し、インターネットからの通信はALBを経由してEC2へ転送する構成とした。
- **捨てたもの**：EC2をPublic Subnetに配置することで、NAT Gatewayを使わずに外向き通信できるシンプルな構成と、NAT Gatewayのコストを抑えられるメリット。
- **承知の上で受け入れた不都合**：Private Subnetに配置したことで、EC2からインターネットへ直接通信できず、パッケージのインストールや更新にはNAT Gatewayなどの外向き通信経路が必要となる。その分、構成が複雑になり、追加コストも発生する。

### 決定：データベースはEC2上に構築せず、Amazon RDSを採用する

- **状況**：可用性・運用性を考慮したAWS構成の設計・構築を学ぶことを優先した。
- **選んだもの**：Amazon RDS（MySQL）。バックアップ・監視・パッチ適用などのマネージド機能を利用できる。
- **捨てたもの**：EC2上にMariaDB／MySQLを構築する構成 — OS管理やバックアップ、パッチ適用などの運用負荷が大きい。
- **承知の上で受け入れた不都合**：OSやDB環境の細かなカスタマイズに制約がある。
- **確かめ方**：RDSの設定画面で、自動バックアップや自動マイナーバージョンアップなどの管理機能が有効になっていることを確認した。

### 決定：RDSはMulti-AZ構成を検討し、今回はSingle-AZで構築する

- **状況**：可用性を高めるためMulti-AZを検討したが、利用中の無料枠ではMulti-AZを選択できなかった。
- **選んだもの**：学習環境ではRDSをSingle-AZで構築する。
- **捨てたもの**：Multi-AZ構成 — 無料枠では選択できないため今回は見送り、今後の機能追加・運用検証時にMulti-AZ構成への変更を検討する。
- **承知の上で受け入れた不都合**：DBを冗長化していないため、障害時に別AZへ自動で切り替えることができない。
- **確かめ方**：RDSの詳細画面でSingle-AZ構成になっていることを確認し、各EC2からMySQL接続を実行して2台ともRDSへ接続できることを確認した。

### 決定：本番想定では各AZにNAT Gatewayを配置するが、検証環境では1台のみ使用する

- **状況**：Private SubnetのEC2からパッケージ取得やアップデートのため外向き通信が必要だったが、NAT Gatewayは利用料金が発生するため、学習環境ではコストを抑える必要があった。
- **選んだもの**：NAT Gatewayを1台のみ作成し、複数AZのPrivate Subnetから共用する構成とした。
- **捨てたもの**：各AZにNAT Gatewayを1台ずつ配置する構成 — 可用性は高まるが、学習環境ではコストが増えるため採用しなかった。
- **承知の上で受け入れた不都合**：NAT Gatewayを配置したAZの障害時は外向き通信ができず、別AZから利用する場合はAZをまたぐ通信が発生する。
- **確かめ方**：各Private Subnetのルートテーブルで `0.0.0.0/0` が同じNAT Gatewayを向いていることを確認し、各AZのEC2でパッケージ取得ができることを確認した。
